# Выпуск контекстной памяти

Ветка разработки: `feat/contextual-memory`; production выпускается только из main.
Новых маршрутов и cron-расписаний нет: используются существующие maintenance и cleanup.

1. Проверить CI на disposable Postgres с применёнными миграциями, включая replay
   старых work items и новые source/reaction/memory сценарии. Не применять тесты
   к production. Для локального Postgres Docker не требуется.
2. Через Supabase tools проверить `work_items`/`work_steps` на незавершённые и
   `ambiguous` работы. Сначала дренировать доступные работы старым deployment;
   неоднозначные отправки разбирать вручную. Не очищать checkpoints и не
   помечать неизвестную отправку завершённой.
3. На время переключения исключить одновременную обработку очереди разными
   deployment (дождаться завершения активных invocation/maintenance). Миграцию
   `contextual_conversation_memory` применить через Supabase tools до build
   production. Все прежние и поставленные старым кодом работы сохраняют версию 1;
   новый enqueue явно пишет 2. Значение нельзя массово менять для начатых работ.
4. Выпустить проверенный main. Новый обработчик продолжает версию 1 по прежнему
   порядку checkpoints, без архивации и новых provider-вызовов. Версия 2 использует
   архив, память и реакции. Не удалять legacy-обработчик, пока остались работы v1.
5. После проверки health/readiness явно зарегистрировать стабильный webhook с
   прежним URL/secret, `max_connections=1`, `drop_pending_updates=false` и типами
   `message`, `edited_message`, `callback_query`. Не регистрировать при startup.
6. Проверить `getMe.can_read_all_group_messages`/privacy mode, членство и реальные
   сообщения в одобренной группе: без тега, reply на старую реплику, источники,
   связанное продолжение автора, «запомни/забудь», 🌚/🗿/🌭 из разрешённого набора.
   Не включать группу скрытым `/init` без явного решения владельца.
7. Отдельно проверить фактические HTTP-результаты maintenance и cleanup, появление
   и завершение `conversation-memory`, состояние внешних удалений, отсутствие
   повторных Telegram send. Только SQL-успех cron не подтверждает выполнение.

Логи `conversation.decided`, `conversation.model_completed`,
`conversation.reacted`, `conversation.reaction_rejected` и существующие work/job
события показывают решения, задержки и ошибки без текста переписки. Mem0 пишет
только безопасные типы исходов. Не выгружать payload/цитаты в общие логи.

Если требуется остановить самостоятельное участие, использовать существующий
read-only `roast-policy.proactiveAllowed=false` либо просьбу «замолчи» в группе.
Прямые обращения и автоматическое извлечение памяти от этого не отключаются.
Откат приложения после начала работ v2 требует их завершения текущим кодом;
старый deployment не умеет продолжать checkpoints v2. Аддитивную миграцию и
служебные tombstone/epoch записи при откате не удалять.
